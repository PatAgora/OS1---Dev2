C1 Vetting Profiles CONFIG
ItemDetail
Pagethe Configuration page → Vetting Profiles section
PurposePre-saved sets of vetting checks that can be applied to projects with one click instead of ticking individual checks each time.
ActionClick "Add Vetting Profile" → enter a name (e.g. "Standard FS", "Enhanced DBS") → tick the checks this profile requires → click Save.
Available ChecksRight to Work, Identity Verification, DBS Check, References, Qualifications, Professional Registration, Credit Check, Directorship / Disqualification, Sanctions / PEP, Social Media Review (10 total)
Vetting Expiry Periods

Separate collapsible section on the Configuration page. Set the expiry period in months for each of the 10 check types. When a check is completed, the system calculates the expiry date from the completion date plus this period.

  • 0 months — check never expires (e.g. Qualifications)
  • 12 months — typical for DBS, Credit Check, Sanctions/PEP
  • 6 months — typical for Social Media Review
  • 36 months — typical for Identity Verification

Expired checks are flagged in red on the candidate profile with a warning icon. Checks approaching expiry (within 40 days) are flagged as "Expiring in X days" on the Placements page.

4 Associate Applies (Behind the Scenes) SYSTEM
What Happens

When an associate submits an application from the portal (see Associate Step 6), the system performs the following automatically:

  • Creates Application record — linked to the Candidate and Job, with initial status "Pipeline"
  • AI Summary auto-generates — Gemini AI reads the associate's CV and produces a plain-text summary of their experience, skills, and suitability
  • AI Match Score auto-generates — Score 0-100 comparing CV to job description, with detailed explanation of scoring rationale
  • Score colour coding: 75+ green (strong match), 50-74 amber (partial match), <50 red (weak match)
Where Staff See It
  • /applications — full applications list with search, filters by project/status
  • /workflow — kanban board showing all applications by stage
  • /candidate/<id> — candidate profile with AI Summary card, AI Match Score sidebar card, and all application detail
Application visible in pipeline

Where

Navigate to /candidate/<id> — scroll to the "Reference Requests" section. Click "Start Referencing".

GATE: The associate must have signed the Employment Reference Declaration (Signable widget on the associate portal) before referencing can begin. If not signed, referencing is blocked.
What Happens When You Click "Start Referencing"
  1. System reads the associate's employment history entries (companies, dates, referee emails, names)
  2. For each entry, creates a ReferenceRequest record with: Company Name, Referee Name, Referee Email, Status ("not_sent")
  3. If no referee email was provided by the associate, the system auto-looks up the company in the Reference Contact Details list (Config C5) and auto-fills the email
  4. The system cross-references each company against the Reference Houses Intel list (Config C5). Flagged companies get an orange warning indicator
  5. If the associate marked "Do not contact" (permission_to_request = No) for a company, the reference is created with "On Hold" status and a red "No permission" badge
  6. References vetting check status → "In Progress"

Where

What Happens Immediately
  1. An email modal opens instantly — pre-loaded with the Vetting Commencement email template (Config C4)

  • Checks marked "Check Still In Date" are skipped by Start Full Vetting and count as complete

Revenue Tab

What each column on /revenue represents and where the data comes from. Applies to both the Client Summary and the per-client engagement table.

R1 Forecast Rev STAFF VIEW
Formula

Σ(charge_rate × planned_count) × working_days × 0.90

Data sources
  • charge_rate — from EngagementPlan, set per role on the engagement plan.
  • planned_count — planned headcount per role on the same engagement plan.
  • working_days — (eng_end − eng_start) × 5/7 (calendar days converted to weekday-equivalents). Narrowed to the active filter window if Date From / Date To / Quarter / Month / Week is set.
  • × 0.90 — 10% shrinkage applied per Req 63 to allow for non-realised days (sickness, holiday, ramp-up, etc.).
What it represents

The realistic revenue ceiling for the engagement over the selected window. Full planned headcount × charge rate × working days, minus 10%.

R2 Cumulative Forecast STAFF VIEW
Formula

Forecast Rev × (elapsed_days_in_window / total_days_in_window)

Data sources
  • Forecast Rev — the column to its left (already shrunk by 10%).
  • total_days — (eng_end − eng_start) over the engagement window.
  • elapsed_days — (today − eng_start), capped at eng_end and floored at 0.
What it represents

"Where we should be by today" — the slice of the full forecast that should already have been billed if delivery is on track. Lets you compare today's Actual Rev against today's expected position rather than against the full lifetime forecast.

R3 Actual Rev STAFF VIEW
Formula

Σ(billable_days × EngagementPlan.charge_rate) per role, for every Approved Timesheet on the engagement, period-bounded

Data sources
  • Timesheet rows — only rows where engagement_id = eng.id AND LOWER(status) = 'approved'. Optionally narrowed to period_end ≥ filter_start AND period_start ≤ filter_end when a date window is active.
  • billable_days — comes off the timesheet itself.
  • charge_rate — comes from the matching EngagementPlan row on the engagement plan (NOT from the timesheet). The match is by role: timesheet → candidate → Application → Job → role_type → EngagementPlan.role_type. Falls back to the engagement-wide weighted-average charge rate if no exact role match exists.
Why charge_rate, not the timesheet's day_rate

Timesheet.day_rate is the associate's PAY rate — what they cost us, not what the client pays. Using it for Actual Rev would conflate cost with revenue. Example: TL on a timesheet has day_rate=£200 (pay), but the engagement plan's TL role has charge_rate=£250. For 5 billable days:

  • Actual Rev = 5 × £250 = £1,250 (what the client is billed)
  • Actual Cost = 5 × £200 = £1,000 (what we pay the associate)
  • Actual Margin = £250
What it represents

Real money the client has been billed (or will be billed) based on what's actually been worked + approved, priced at the agreed charge rate.

Why an unstarted engagement reads £0

If no timesheets have been approved for that engagement yet (e.g. associate hasn't started), this column is £0. That's correct — before Req 63 this column was a random simulation, which is why an unstarted engagement could still show a number.

R4 Forecast Margin STAFF VIEW
Formula

Forecast Rev − (Σ pay_rate × planned_count × working_days)

Data sources
  • Forecast Rev — already shrunk by 10%.
  • forecast_cost = Σ(EngagementPlan.pay_rate × EngagementPlan.planned_count) × working_days — the daily pay you'd be paying associates if planned headcount were billing every day in the window.
Note on shrinkage

Shrinkage is applied to the revenue side only — cost is on a "best case" full-headcount basis. So Forecast Margin reflects expected gross margin assuming the plan delivers fully.

R5 Actual Margin STAFF VIEW
Formula

Actual Rev − Actual Cost

where:

  • Actual Rev = Σ(billable_days × EngagementPlan.charge_rate) across approved timesheets (R3 above).
  • Actual Cost = Σ(billable_days × Timesheet.day_rate) across the same timesheets — the associate's PAY rate as recorded on each timesheet.
What it represents

The true gross margin on what's actually been worked + approved — client billing minus associate pay, summed across every approved timesheet in the window.

No more proxy

Earlier this column used a "cost ratio" derived from the plan's average to apportion cost from revenue. That's gone — cost now reads directly from each timesheet's pay rate, so margin is exact even when an associate's pay rate differs from the plan's average for that role.

Worked example

TL on a 5-day timesheet, pay rate £200/day. Engagement plan TL role charge_rate £250/day.

  • Actual Rev: 5 × 250 = £1,250
  • Actual Cost: 5 × 200 = £1,000
  • Actual Margin: £250
R6 Variance STAFF VIEW
Formula

Actual Rev − Forecast Rev (computed in the template, not the backend).

What it represents

How far the engagement is over (positive, green) or under (negative, red) the full lifetime forecast.

Watch out

Not useful early in an engagement — Forecast Rev covers the entire window, not just elapsed time. Compare Actual Rev vs Cumulative Forecast for real-time progress against plan; use Variance only to assess delivery against the full lifetime forecast.

R7 Where it lives in code REFERENCE
  • Per-engagement calculation: app.py — the loop building client_data[client_name]["engagements"] in the /revenue route.
  • Per-client roll-up: the += accumulators inside the same loop.
  • Cumulative Forecast formula: inline in the same loop just before the per-engagement append.
  • Actuals SQL: the approved-Timesheet query bounded by the same date filters.
  • Header labels: templates/revenue.html — Client Summary table and per-client engagement table use identical column orders.
Sanity check if numbers look off

Empty EngagementPlan rows produce £0 Forecast Rev (and therefore £0 cumulative + 0 margin). If a client reads zero across the board: check the engagement has at least one EngagementPlan row with charge_rate and pay_rate filled in.
